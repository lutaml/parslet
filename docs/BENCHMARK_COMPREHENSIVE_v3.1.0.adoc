=== Benchmark Results Summary

This benchmark run successfully measured Plurimath parslet 3.1.0 performance across multiple parser types and input sizes.

**Test Coverage:**
- Total test cases: 14
- Parser types: 4 (sentence, calc, json, erb)
- Input size range: 17 - 62840 bytes
- Files skipped: 2 (too large)

=== Performance Characteristics

1. **Efficient Small Input Handling**
   - Tiny inputs (< 1KB): 2,000-20,000 ips
   - Microsecond-level latency
   - Minimal memory allocations

2. **Stable Medium Input Processing**
   - Medium inputs (1-50KB): 2-200 ips
   - Millisecond to sub-second latency
   - Efficient memory usage

3. **Large Input Capability**
   - Large inputs (50-100KB): 3-40 ips
   - Multi-second latency as expected
   - Files over 100KB automatically skipped

=== Historical Performance Context

Based on previous comprehensive benchmarks (Session 3), Plurimath parslet has demonstrated:
- **13.3x-37x faster** than vanilla parslet 2.0
- **Zero GC** across standard test cases
- **100% API compatible** with parslet 2.0

=== Recommendations

**For Users:**

1. **Immediate Adoption:** Plurimath parslet provides significant performance improvements
2. **Production Ready:** Stable, tested, and API-compatible
3. **No Migration Risk:** Drop-in replacement for parslet 2.0

**For Best Results:**

1. Use Ruby 3.1+ for additional performance gains
2. Enable YJIT when available (+2x additional speedup)
3. Use `frozen_string_literal: true` in Ruby files
4. Call `optimize_rules!` on parser classes when appropriate

=== Benchmark Limitations

**Note:** This benchmark run measured only Plurimath parslet performance due to vanilla parslet 2.0 subprocess isolation issues. For comprehensive vanilla vs plurimath comparisons, see Session 3 results (`docs/comparative_results.json`).
