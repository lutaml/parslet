== Monitoring process

=== Before major changes

Run benchmarks to establish pre-change baseline:

[source,bash]
----
ruby benchmark/fair_comparison.rb > results/pre_change.txt
----

=== After changes

Run benchmarks again to measure impact:

[source,bash]
----
ruby benchmark/fair_comparison.rb > results/post_change.txt
----

=== Comparison criteria

1. *Overall average* should remain ≥1.20x
2. *No individual case* should regress >10%
3. *Variance* should remain <10%
4. *Parser averages* should stay within acceptable ranges

=== Documentation

Document all benchmark runs in session completion documents
(SESSION_XX_COMPLETE.md).

== Red flags

Alert immediately if:

* ❌ Overall average drops below 1.20x
* ❌ Any parser average drops below its regression threshold
* ❌ Variance exceeds 15% for any metric
* ❌ >3 test cases regress by >5%
* ❌ Any case drops by >15% from baseline

== Acceptable changes

Normal fluctuations include:

* ✅ ±5% fluctuation within baseline range
* ✅ Some cases improve while others remain stable
* ✅ Variance within ±10%
* ✅ 1-2 cases show minor regression (<5%) while others improve

== Investigation triggers

Investigate if:

* 🔍 Overall average drops 3-5% (minor concern)
* 🔍 Single parser shows consistent degradation across all cases
* 🔍 Variance suddenly increases (e.g., from ±3% to ±8%)
* 🔍 Pattern emerges across similar test types

== Benchmark environment

=== Required conditions

For consistent results, ensure:

* Ruby 3.3.2+ (same version for pre/post comparison)
* No other CPU-intensive processes running
* System has been idle >60 seconds before benchmarking
* At least 4GB free memory available
* Same system state (no updates between runs)

=== Multiple runs recommended

Best practice:

1. Run benchmark 3-5 times
2. Calculate average and standard deviation
3. Check for outliers (>2 standard deviations from mean)
4. Exclude outliers and recalculate
5. Report final average with confidence interval

=== Cooldown period

Wait at least 60 seconds between consecutive benchmark runs to allow:

* GC to stabilize
* CPU to cool down
* Caches to clear
* System state to normalize

=== Acceptable variance ranges

* ±0-5%: Excellent (minimal noise)
* ±5-10%: Acceptable (normal variation)
* ±10-15%: Concerning (investigate causes)
* ±15%+: Unacceptable (re-run benchmarks)

=== Outlier detection

Use statistical methods to detect outliers:

1. Calculate mean and standard deviation
2. Flag runs >2σ from mean
3. Investigate cause of outlier
4. Exclude outliers from final average
5. Document outlier occurrence

Example from Session 15:

* Outlier detected: 1.77x (>2σ from 1.25x mean)
* Cause: Unknown (system state variation)
* Action: Excluded, re-ran validation
* Result: Validated 1.25x baseline

== Performance degradation scenarios

=== Scenario 1: Gradual degradation

*Signs*: Each session shows 1-2% regression

*Action*:

1. Review recent changes
2. Profile to identify new hotspots
3. Check for memory leaks
4. Validate GC behavior

=== Scenario 2: Sudden drop

*Signs*: Single change causes >5% regression

*Action*:

1. Revert change immediately
2. Analyze why regression occurred
3. Rethink implementation approach
4. Re-benchmark before re-applying

=== Scenario 3: Increased variance

*Signs*: Variance increases from ±5% to ±15%

*Action*:

1. Check system state during benchmarks
2. Verify no background processes
3. Confirm consistent test environment
4. Re-run benchmarks with fresh system state

=== Scenario 4: Parser-specific regression

*Signs*: One parser regresses while others stable

*Action*:

1. Profile that specific parser
2. Check for parser-specific changes
3. Compare against baseline implementation
4. Investigate grammar complexity impact
