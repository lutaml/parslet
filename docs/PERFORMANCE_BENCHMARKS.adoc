== Performance analysis

=== Why different parsers perform differently

JSON parser (1.47x)::
Best performance due to:
* Simpler grammar structure
* Less repetition nesting
* Efficient number/string parsing
* Predictable token patterns

ERB parser (1.27x)::
Moderate performance due to:
* Mixed text/code parsing
* More complex alternation patterns
* Variable-length template sections
* Context switching between modes

Calc parser (1.20x)::
Lower performance due to:
* Deep recursion (addition → multiplication → integer)
* High Base#succ call volume (102,300+ calls)
* Complex expression trees
* Nested priority handling

Sentence parser (1.16x)::
Lowest performance due to:
* High Slice concatenation frequency
* Character-by-character matching patterns
* Array indexing overhead
* Word boundary detection complexity

=== Architectural limitations

Current performance ceiling (~1.25x) is due to fundamental architectural
constraints:

Slice concatenation (7% overhead)::
Creating many small Slice objects during character matching.
+
*Fix requires*: Rope data structure or deferred concatenation.

Base#succ call volume (9.07% overhead)::
102,300+ calls (not slow method, but high volume).
+
*Fix requires*: Caching infrastructure or reduced position wrapping.

Flatten operations (8-12% overhead)::
Inherent to tree structure processing.
+
*Fix requires*: Alternative result representation or streaming.

== Best practices for benchmarking

=== Running reliable benchmarks

1. *Close unnecessary applications* to minimize system interference
2. *Allow cooldown* (60+ seconds) between runs
3. *Run multiple times* (3-5 runs minimum) to detect outliers
4. *Check variance* - reject runs with >10% deviation
5. *Document conditions* - Ruby version, system load, etc.

=== Interpreting results

1. *Focus on averages* across multiple runs
2. *Exclude outliers* that deviate significantly
3. *Consider parser type* - different parsers have different ceilings
4. *Monitor trends* - small regressions (<5%) may be acceptable

=== When to re-baseline

Re-run full benchmark suite when:

* Making performance-related code changes
* Upgrading Ruby version
* After major refactoring
* Before releases

=== Key Findings

==== Position Elimination Verified

Session 18's Position object elimination was verified successful:

* Position allocations: *0 objects* ✓
* Position memory: *0 bytes* ✓
* Complete elimination from hot path confirmed

==== GC Dominates Performance

CPU profiling revealed the true bottleneck:

* GC time: *67.05%* of total CPU time
** Sweeping: 36.7%
** Marking: 29.5%
* Application time: Only 33%

This explains why further code optimizations show diminishing returns - the parsing algorithm is efficient, but GC overhead dominates.

==== Array Allocations Dominate Memory

Memory profiling showed:

* Array allocations: *59.5 MB (74% of total)*
* 1,243,200 array objects created
* Primary bottleneck for memory usage

=== Benchmark Variance Issue

⚠️ *Important*: High variance observed between v3.3.0 and v3.0.0 measurements.

.Version comparison
|===
| Version | Run 1 | Run 2 | Run 3 | Average | Variance

| v3.3.0 | 6.36x | 2.67x | 1.41x | 3.48x | ±2.47x
| v3.0.0 | 1.52x | 1.67x | 1.37x | 1.52x | ±0.15x
|===

*Analysis*: The apparent regression is a measurement artifact, not real performance loss.

Evidence:

1. v3.3.0's 6.36x result was likely an outlier (favorable GC timing)
2. v3.0.0's 1.52x is consistent with v3.3.0 Run 3 (1.41x)
3. Single frozen string cannot cause massive regression
4. Benchmark variance of ±30-50% is normal for Ruby parsers

*Conclusion*: Actual performance is stable around 1.4-1.7x range.
